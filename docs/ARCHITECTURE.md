# BotFlow — архитектурные границы
Статус: документ разделяет текущую реализацию и целевую модель. Он не означает, что целевая модель уже реализована.

Дата: 26.08.2026.

## 1. Текущий runtime

```text
Telegram Mini App (React + Vite)
        │ initData / REST
        ▼
FastAPI API ───────────────► PostgreSQL / SQLAlchemy / Alembic
        │
        ├── aiogram: главный бот и клиентские Telegram-боты
        ├── Telegram webhooks
        ├── payment webhooks
        └── APScheduler: дожимы и фоновые операции
```

Существующее ядро построено вокруг `BotConfig`, Telegram-токена и JSON-схемы воронки. Оно остаётся рабочим контуром до поэтапной миграции.

## 2. Целевая доменная модель

```text
Account
├── Bot
│   ├── Scenario
│   ├── PlatformConnection[]
│   ├── GatewayConnection binding
│   ├── Offer[]
│   ├── Lead[]
│   ├── Broadcast[]
│   ├── MetricDaily[]
│   └── BotSubscription
├── GatewayConnection[]
└── GiftGrant[]
```

Новые сущности вводятся только миграциями и совместимыми шагами. Большое переписывание всего проекта одним релизом запрещено.

## 3. Границы ответственности

- **Account** отвечает за владельца, библиотеку касс, платежи BotFlow и подарки.
- **Bot** является границей публикации, оплаты подписки и пользовательского workspace.
- **Scenario** отвечает только за поведение и контент бота.
- **PlatformConnection** отвечает за транспорт и credentials платформы.
- **GatewayConnection** отвечает за credentials, webhook и проверку кассы.
- **PaymentOrder** отвечает за неизменяемый снимок покупки лида.
- **Fulfillment** отвечает за идемпотентную выдачу.
- **Entitlement/Billing** отвечает за право публикации конкретного бота.

API-роутер не должен постепенно превращаться в место реализации всех этих правил. Доменные инварианты выносятся в сервисы только при реальной необходимости изменения соответствующего сценария.

## 4. Обязательные инварианты

1. Любое изменение или чтение bot-scoped данных проверяет владельца.
2. Бот нельзя опубликовать, если серверная readiness-проверка не пройдена.
3. Frontend не является источником истины для готовности, оплаты или прав.
4. Секреты касс и платформ шифруются и никогда не возвращаются полностью через API.
5. Webhook проверяется по провайдеру, подключению и неизменяемому payment snapshot.
6. Повторный webhook безопасен и не создаёт повторную выдачу.
7. Успешная оплата и выдача фиксируются транзакционно либо через надёжную повторяемую fulfillment-задачу.
8. Старые счета продолжают обрабатываться старым подключением после переключения кассы у бота.
9. Telegram `file_id` принадлежит конкретному токену бота; при замене токена медиа требует пересинхронизации.
10. Ошибка внешнего API не маскируется ответом «успешно» в пользовательском интерфейсе.

## 5. Состояния бота

Минимальная целевая машина:

```text
draft → ready → published
  ▲       │         │
  └───────┴── paused┘
                 │
              archived
```

- `draft` — можно редактировать и тестировать владельцем;
- `ready` — конфигурация валидна, но ещё не опубликована;
- `published` — подписка и обязательные интеграции активны;
- `paused` — остановлен вручную, из-за оплаты или критической интеграции;
- `archived` — не участвует в работе, данные сохранены по политике хранения.

Причина паузы хранится отдельно от общего статуса.

## 6. Платёжный контур

```text
Lead
  → выбирает Offer
  → создаётся PaymentOrder snapshot
  → provider checkout
  → проверенный webhook
  → transition payment state
  → idempotent Fulfillment
  → уведомления
  → аналитика
```

Для каждого перехода должен существовать стабильный внешний или внутренний idempotency key и журнал результата.

## 7. Платформенная эволюция

Telegram остаётся единственным исполняемым адаптером v1. Общие доменные правила не должны зависеть от `telegram_id`, однако текущий Telegram-код не переписывается заранее без этапа внедрения VK или MAX.

При добавлении новой платформы создаётся адаптер с единым контрактом:

- проверить credentials;
- настроить/удалить webhook;
- отправить сообщение и медиа;
- сопоставить внешнего пользователя с Lead;
- сообщить capability limits.

## 8. Миграционная стратегия

1. Зафиксировать контракты и тесты текущего поведения.
2. Ввести новую сущность рядом со старой.
3. Выполнить backfill и проверку данных.
4. Перевести чтение на новую модель.
5. Перевести запись.
6. Удалять legacy только после наблюдаемого стабильного периода.

Каждый шаг должен быть обратим миграцией или feature flag там, где риск высок.

## 9. Наблюдаемость

Обязательные структурированные события:

- создание/публикация/пауза бота;
- проверка Platform/Gateway Connection;
- создание и изменение статуса счёта;
- получение и отклонение webhook;
- начало, успех и ошибка выдачи;
- запуск и результат рассылки;
- изменение подписки бота;
- административное действие.

Логи не содержат токены, secret keys, полные платёжные реквизиты и персональные данные без необходимости.
