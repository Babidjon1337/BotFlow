# BotFlow — план развития
Статус: актуальный roadmap после product discovery 26–27.08.2026; порядок выполнения ревизии 28.08.2026 (согласован с владельцем).

Главный принцип: эволюция без большого переписывания. Каждый этап делится на небольшие проверяемые изменения и не начинается, пока предыдущий не имеет зелёных проверок.

## Порядок выполнения (ревизия 28.08.2026)

```text
R7 (рассылки: scheduled + cancel) → R4.1 (Welcome v2) → R4.5 (DS v2: токены, шрифты, shell, базовый кит)
→ R4.2 / R4.3 (полировка рабочих областей) → R5 → R6 → R8 → R9 → R10 (оставшиеся экраны) → R11
```

Номера этапов сохранены для обратной совместимости ссылок (CONTEXT.md, доки) — порядок задаётся этим блоком, а не номером.

## Приоритет решений

1. Корректная оплата и гарантированная выдача.
2. Честные права публикации и жизненный цикл бота.
3. Понятный путь от Welcome до работающего бота.
4. Единая рабочая область аккаунта и бота.
5. Удобство сценария, аудитории и аналитики.
6. Визуальная полировка.
7. Будущие платформы и сценарии.

Статус: выполнено. Реализация зафиксирована в `6fd7179` и `f684af4`; ручной

### Что сделать

1. Сопоставить каждый новый экран с существующей работающей функцией.
2. Вернуть достижимость реализованных сценария, Dashboard с клиентами и аналитикой, настроек и админки.

3. Проверить guard несохранённых изменений и переключение ботов.
4. Удалить только доказанно осиротевшие компоненты после проверки импортов.
5. Исправить текущие lint/TypeScript/test failures.
6. Провести browser smoke на desktop и Telegram mobile viewport.

### Результат

### API

## R3. Черновик, расчёт цены и публикация

Статус: CLOSED. Совместимые модели `GatewayConnection` и
`BotSubscription`, entitlement boundary, deterministic v1 quote и
per-bot publication switch уже добавлены. Если у бота есть
`BotSubscription`, публикацию определяет только она; если записи нет,
сохраняется legacy account-level маршрут до явного переноса. Продаваемая
конфигурация пока ровно одна: Telegram + «Воронка продаж» за 990 ₽/мес.
VK, MAX и будущие сценарии отклоняются серверным pricing contract и
показываются клиенту только как «Скоро»; checkout ещё не переключён.

R3 gate закрыт: `alembic heads` указывает на `a4d2e7f93c01`, полный backend
suite — 75 passed. Expiry job берёт подписку в атомарный lease, чтобы не
остановить только что продлённый бот; legacy PRO-expiry исключает ботов с
`BotSubscription`.

### Поведение

- черновиков может быть несколько;
- внешний пользователь не проходит неопубликованный бот;
- владелец может тестировать свой черновик;
- конфигуратор рассчитывает цену конкретного бота;
- первая платформа включена, дополнительные увеличивают цену;
- trial отсутствует;
- публикация требует активной оплаты этого бота; Gift Grant — отдельный
  последующий runtime-этап;
- окончание подписки ставит только этот бот на паузу.

### Сервисы

- `BotPricingService` — детерминированный расчёт конфигурации;
- `BotEntitlementService` — право публикации конкретного бота;
- `BotLifecycleService` — единый запуск/пауза/возобновление;
- серверный `ReadinessService` остаётся источником истины.

Gate: матрица прав, повторная оплата, истечение, возобновление и изоляция нескольких ботов.

## R5. Воронка продаж

### Модель

- режимы `autopay`, `application`, `hybrid`;
- старт;
- дожимы 0–5;
- предложения с индивидуальной выдачей;
- единый media attachment;
- сохранение только при реальном diff;
- версия сценария для создаваемого счёта.

### UX

- последовательность видна без отдельной декоративной схемы;
- длинные тексты удобно редактировать на телефоне;
- фокус не скрывается под клавиатурой/navigation;
- tariff/offer-секция не превращается в бесконечный скролл;
- ошибки readiness ведут к конкретному полю.

Gate: все режимы, 0/1/5 дожимов, один/несколько offers, media replacement, token replacement, dirty-state.

## R6. Payment & Fulfillment Reliability

### Общий контракт провайдеров

- create payment;
- verify credentials;
- verify webhook;
- fetch authoritative status;
- normalize failed/canceled/succeeded;
- capability flags для чеков, рассрочки и возвратов.

### Надёжность

- immutable PaymentOrder snapshot;
- webhook маршрутизируется по Gateway Connection;
- idempotency для webhook и выдачи;
- старые счета используют старую кассу;
- повторная обработка безопасна;
- владелец получает обязательное уведомление через главный BotFlow;
- лид получает понятную ошибку без технических деталей;
- Dashboard обновляется только подтверждёнными данными.

Проверить отдельно YooKassa, Robokassa и Prodamus. Непроверенный провайдер скрывается или явно маркируется beta, но не объявляется равноправно рабочим.

Gate: реальные sandbox/contract tests и сценарии с повторными webhooks.

## R7. Аудитория и рассылки

Статус: частично реализовано (каркас готов, ревизия 28.08.2026). Уже есть:
модель `Broadcast` + `BroadcastRecipient` с claim-защитой от дублей, чанковая
отправка (~20 msg/с, обработка flood-wait), scheduler-джоба
`process_broadcasts_job`, API `audience/summary`, `audience`, `broadcasts`
(create/list/detail/retry), экран `BroadcastsScreen` (аудитория:
все/оплатившие/без оплаты + история рассылок) и `BroadcastComposerSheet`.

### Осталось сделать (текущая итерация)

- scheduled: колонка `scheduled_at` + миграция; джоба берёт только созревшие;
  создание рассылки с датой отправки;
- `POST /api/broadcasts/{id}/cancel` — атомарно переводит queued/scheduled в
  `cancelled`, безопасно при гонке с claim;
- UI: выбор «Отправить сейчас / Запланировать» в композере (локальная таймзона),
  «Отменить» для scheduled/queued, «Повторить» для failed, бейджи статусов;
- pytest: scheduled не уходит раньше времени; cancel до и во время; подсчёт
  получателей; retry только failed; изоляция ботов.

### Область этапа

- аудитория конкретного бота;
- лид определяется по `bot × platform × external identity`;
- фильтры все/оплатившие/неоплатившие;
- создание рассылки из Audience hub;
- одна платформа выбирается автоматически;
- несколько — только из оплаченных и подключённых;
- draft/scheduled/sending/sent/failed;
- батчи, повторяемость и защита от дублей.

Gate: корректный подсчёт получателей, отмена scheduled, повтор failed, изоляция ботов.

## Правила выполнения roadmap

- один логический commit — одна проверяемая причина изменения;
- описание commit на русском;
- миграции и API меняются раньше зависимого UI;
- новый UI не скрывает существующую функцию без продуктового решения;
- крупная несвязанная находка фиксируется в roadmap, но не расширяет текущий PR;
- нельзя переходить к следующему этапу при красном gate;
- после этапа: изменения, проверки, ручной QA, риски и оценка готовности.
